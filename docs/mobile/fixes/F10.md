# F10 (P2): aim line under the hero sprite (touch aim)

## Problem

On touch devices the dashed aim line, drawn from the hero to the aim point while an
ability button is held and dragged, was painted on top of the hero sprite and crossed
the hero's face.

## Root cause

`public/hero-lab/world.js` (before this fix, at `a00488c`):

- `drawScene` (line 5102) painted the arena in one long hand-ordered function with no
  explicit layer order. The hero sprites are drawn in the players loop
  (`// 3. Draw players`, line 5530; the sprite itself at line 5654).
- The touch aim was drawn by `drawTouchAim(currentTime)` at **line 5971**, the very last
  world-space call, after the heroes, projectiles, particles and damage numbers.
- `drawTouchAim` (line 6337) drew the line (`moveTo(player.x, player.y)` ->
  `lineTo(visual.to…)`, line 6347) and the end reticle in the same pass. Because the
  line starts at the hero's centre and was drawn last, it lay over the sprite.

The Ranger's bow / Dead Aim guide (`drawRangerAimGuides()`, line 5230) was already drawn
before the enemies, so it was under the sprite. Only the touch aim line was wrong.

## Fix

1. **Explicit draw order.** `public/hero-lab/game-config.js` now exports
   `ARENA_DRAW_ORDER` (bottom to top), next to the other mobile constants:

   `ground, campfireRings, campfire, aimLines, shadows, enemies, worldMarkers, heroes,
   effects, aimReticle, screenEffects, hud`

2. **The render loop follows the list.** In `world.js`, `drawScene` still sets up the
   frame (HUD throttle, touch camera, shake and boss-zoom transforms) and then runs
   `for (const layerId of ARENA_DRAW_ORDER)`, calling one painter per layer from the
   `ARENA_LAYERS` map (`paintGroundLayer`, `paintCampfireRingsLayer`,
   `paintCampfireLayer`, `paintAimLinesLayer`, `paintShadowsLayer`, `paintEnemiesLayer`,
   `paintWorldMarkersLayer`, `paintHeroesLayer`, `paintEffectsLayer`,
   `paintAimReticleLayer`, `paintScreenEffectsLayer`; `hud` is the DOM HUD above the
   canvas, so it has no canvas pass). The painters hold the drawing code that was
   already in `drawScene`, in the same order, cut at the layer boundaries. The first
   screen-space layer closes the world transform (`endArenaWorldPass`, the same reset
   code as before). A startup check logs an error if a listed layer has no painter.
3. **The touch aim is split into two passes.** `drawTouchAimLine()` runs in `aimLines`,
   together with `drawRangerAimGuides()` (the Ranger's bow line and Dead Aim line), so
   both are under shadows, enemies and hero sprites. The line still starts at the
   hero's centre and the sprite covers the start. `drawTouchAimReticle()` (the small end
   ring and dot) runs in `aimReticle`, above enemies and effects, so the target point
   stays visible. The colour, alpha, width, dash and geometry are unchanged.
4. **Enemy shadows are their own layer.** The shadow ellipse used to be drawn inside
   each enemy's loop iteration. It now runs as a separate pass before all enemy sprites,
   at the same position (`enemyDrawOffset`, shared with the enemy pass, which still
   expires the hit knock-back).

Unchanged: aim logic, the messages sent to the server (the e2e test checks that one
`skill` is sent on release), balance, server code, and the depth of the area markers and
the Engineer's laser aim line (both still in `worldMarkers`, above enemies and below
heroes, as before). `web/src/teacher/` is untouched. On desktop the only visible
difference is that, where two enemies overlap, one enemy's shadow no longer covers the
other enemy's sprite.

## Assumptions

- **Area markers.** The brief lists "area markers and rings" under the aim lines, but
  also says not to move the area markers or the Engineer's laser aim line (the
  instructions for this task repeat that). I took "do not move" as the stronger
  rule. The permanent campfire heal and Thorns rings (and the Fairy vortex floor ring in
  `ground`) are the rings below the aim lines. The transient area-effect telegraphs and
  detonations, spawn telegraphs, traps and the Engineer laser stay where they were, in
  `worldMarkers` between enemies and heroes. A translucent telegraph that overlaps the
  aim line therefore tints it, as it already tinted the Ranger's bow line.
- **Campfire.** The campfire sprite, its glow and the Fairy vortex structures were
  already drawn before the Ranger aim line, so they get their own `campfire` layer
  between the rings and the aim lines.
- **Other hero-origin guides.** The non-Ranger aim triangle and the hero's own blue
  ring are drawn in the hero pass before the sprite, so they were already under it.
  The Samurai cut guide is drawn over enemies but under the hero by an earlier design
  decision (a comment in the code says so). It is a dash path, not an aim line, so it
  stays in `worldMarkers`.
- **Hero shadows** are part of the hero sprite art, so `shadows` means enemy shadows.
- **HUD.** The HUD is DOM above the canvas. `hud` is listed last for completeness and
  has no canvas pass.
- The worktree was created from `main`. I reset it to `mobile-fixes` (`a00488c`) before
  starting, as the task asks.

## Tests

New tests:

- `tests/mobile/arena-draw-order.unit.test.mjs` (node:test, part of
  `npm run test:mobile:unit`): the list is frozen and has no duplicates. It checks the
  required relative order (ground < rings < aim lines < shadows < enemies < heroes <
  effects < reticle < HUD, with HUD last), that the area markers and Engineer laser stay
  between enemies and heroes, and that `drawScene` iterates `ARENA_DRAW_ORDER`. It also
  checks that the `ARENA_LAYERS` painter keys equal the list in order, and that the touch
  line, the Ranger guide and the reticle are each called once, from the right layer.
- `tests/mobile/aim-line-layer.e2e.mjs` (Playwright, part of `npm run test:mobile`):
  this test opens the arena sandbox as a 667 x 375 touch phone with Guardian, whose blue
  line cannot be confused with the grey helmet. It waits for the sprite cache (lobby
  icon), takes a screenshot, holds an E drag upward through CDP touch, and takes a
  second screenshot. In the page it rebuilds the sprite's on-screen alpha from the same
  image, config and camera maths (`touch-controls.js`) the game uses to get the sprite's
  bounding box. It asserts that no pixel inside that box turned aim-line coloured
  between the two shots, and that the line is visible above the hero (more than 20 such
  pixels), so the test cannot pass vacuously. It also checks that release sends exactly
  one `skill` and that there are no page errors. It uses no sleeps, only waits on state
  and `requestAnimationFrame`.
  - Against the old code it fails: 54 aim-line pixels inside the box. With the fix: 0.
